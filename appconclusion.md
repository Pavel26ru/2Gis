
# Анализ сервиса бронирования отелей

## Общее описание

Сервис представляет собой REST API для бронирования номеров в отелях. На данный момент реализована только одна функция: 
создание бронирования. Сервис написан на Go и использует следующие основные компоненты:

- **Веб-фреймворк:** `chi`
- **Архитектура:** Слоистая (контроллеры, сервисы, репозитории)
- **База данных:** In-memory хранилище

## Проблемы и слабые места

### 1. Архитектура и разделение ответственностей

- **Смешение зон ответственности:** Репозиторий `orderMemoryRepository` выполняет не только функции хранения данных, 
- но и бизнес-логику по проверке доступности номера (`isRoomAvailable`) и проверке существования номера (`isKnownRoom`).
- Эту логику следует перенести на уровень сервиса.
- **Недостаточная абстракция:** Интерфейс `OrdersRepository` содержит только один метод `Create`. Для дальнейшего 
- развития потребуется расширение интерфейса (например, для получения данных о бронированиях), что может нарушить принцип разделения интерфейсов.
- **Валидация в контроллере:** Валидация данных запроса (`validateCreateOrder`) находится в слое контроллера. 
- Эту логику лучше перенести в сервисный слой, чтобы обеспечить консистентность данных независимо от точки входа.

### 2. Конкурентность

- **Гонка данных (Data Race):** В `orderMemoryRepository` методы `Create` и `isRoomAvailable` обращаются к общему срезу 
- `orders` без какой-либо синхронизации. При одновременном выполнении нескольких запросов на бронирование одного и того же 
- номера возможна ситуация, когда оба запроса успешно пройдут проверку доступности и создадут бронирование, что приведет
- к двойному бронированию. Для решения этой проблемы необходимо использовать мьютексы (`sync.Mutex` или `sync.RWMutex`)
- для защиты доступа к `orders`.

### 3. Обработка ошибок

- **Неинформативные ошибки:** В `CreateOrderHandler` все ошибки, возвращаемые из сервисного слоя, обрабатываются как
- `http.StatusInternalServerError`. Это скрывает от клиента реальную причину ошибки (например, "комната недоступна" или 
- "неверные даты"). Необходимо ввести кастомные типы ошибок и обрабатывать их в контроллере, возвращая соответствующие 
- HTTP-статусы (например, `http.StatusBadRequest` для ошибок валидации, `http.StatusConflict` для уже забронированной комнаты).
- **Паника в `main`:** При ошибке запуска сервера (`http.ListenAndServe`) приложение паникует. Это не самый лучший способ
- обработки ошибок в `main`. Лучше использовать `log.Fatal` для логирования ошибки и завершения работы приложения.

### 4. Структура проекта

- **Неполная структура:** Отсутствуют директории для конфигурации, доменных моделей и утилит. Это может затруднить
- дальнейшее развитие проекта.
- **DTO в качестве доменной модели:** Структура `dto.Order` используется как для передачи данных между слоями, 
- так и для представления доменной сущности. Это может привести к проблемам при развитии, когда представление данных 
- в API и в доменной модели начнет различаться.

### 5. Потенциальные доработки

- **Интеграция с базой данных:** Заменить in-memory репозиторий на реальную базу данных (например, PostgreSQL).
- Для этого потребуется определить интерфейс репозитория, который будет работать с базой данных, и реализовать его.
- **Отправка письма-подтверждения:** Добавить сервис для отправки email-уведомлений. Это можно сделать с помощью
- асинхронной обработки задач (например, с использованием `goroutines` и каналов или брокера сообщений).
- **Аутентификация и авторизация:** Добавить middleware для проверки прав доступа к API.
- **Конфигурация:** Вынести конфигурационные параметры (адрес сервера, параметры подключения к базе данных) в отдельный
- файл или переменные окружения.
- **Логирование:** Использовать более продвинутый логгер (например, `logrus` или `zap`) для структурированного логирования.
- **Тестирование:** Написать юнит-тесты для сервисов и репозиториев, а также интеграционные тесты для API.

## Рекомендации по рефакторингу

1.  **Перенести бизнес-логику из репозитория в сервис:**
    -   В `OrdersService` добавить методы `isRoomAvailable` и `isKnownRoom`.
    -   `OrdersRepository` должен заниматься только CRUD-операциями.

2.  **Обеспечить потокобезопасность:**
    -   В `orderMemoryRepository` добавить `sync.RWMutex` и использовать его для защиты доступа к `orders`.

3.  **Улучшить обработку ошибок:**
    -   Создать кастомные типы ошибок (например, `ErrRoomNotAvailable`, `ErrInvalidDateRange`).
    -   В `CreateOrderHandler` обрабатывать эти ошибки и возвращать соответствующие HTTP-статусы.

4.  **Разделить DTO и доменную модель:**
    -   Создать пакет `domain` с доменной моделью `Order`.
    -   В сервисах работать с доменной моделью, а в контроллерах преобразовывать DTO в доменную модель и обратно.

## Структура БД для масштабирования

Для поддержки миллиона пользователей в сутки потребуется хорошо спроектированная и масштабируемая структура базы данных.
Вот пример такой структуры с использованием PostgreSQL:

### Таблицы

1.  **`hotels`** - информация об отелях
    -   `id` (BIGSERIAL, PRIMARY KEY) - уникальный идентификатор отеля
    -   `name` (VARCHAR) - название отеля
    -   `address` (VARCHAR) - адрес
    -   `created_at` (TIMESTAMPTZ) - время создания
    -   `updated_at` (TIMESTAMPTZ) - время обновления

2.  **`room_types`** - типы номеров
    -   `id` (BIGSERIAL, PRIMARY KEY) - уникальный идентификатор типа номера
    -   `hotel_id` (BIGINT, FOREIGN KEY to `hotels.id`) - идентификатор отеля
    -   `name` (VARCHAR) - название типа номера (например, "стандарт", "люкс")
    -   `description` (TEXT) - описание
    -   `price` (DECIMAL) - цена за ночь
    -   `created_at` (TIMESTAMPTZ)
    -   `updated_at` (TIMESTAMPTZ)

3.  **`rooms`** - конкретные номера
    -   `id` (BIGSERIAL, PRIMARY KEY) - уникальный идентификатор номера
    -   `room_type_id` (BIGINT, FOREIGN KEY to `room_types.id`) - идентификатор типа номера
    -   `number` (VARCHAR) - номер комнаты (например, "101", "202a")
    -   `created_at` (TIMESTAMPTZ)
    -   `updated_at` (TIMESTAMPTZ)

4.  **`users`** - пользователи
    -   `id` (BIGSERIAL, PRIMARY KEY) - уникальный идентификатор пользователя
    -   `email` (VARCHAR, UNIQUE) - email пользователя
    -   `password_hash` (VARCHAR) - хеш пароля
    -   `created_at` (TIMESTAMPTZ)
    -   `updated_at` (TIMESTAMPTZ)

5.  **`orders`** - бронирования
    -   `id` (BIGSERIAL, PRIMARY KEY) - уникальный идентификатор бронирования
    -   `user_id` (BIGINT, FOREIGN KEY to `users.id`) - идентификатор пользователя
    -   `room_id` (BIGINT, FOREIGN KEY to `rooms.id`) - идентификатор номера
    -   `from_date` (DATE) - дата заезда
    -   `to_date` (DATE) - дата выезда
    -   `status` (VARCHAR) - статус бронирования (например, "pending", "confirmed", "cancelled")
    -   `created_at` (TIMESTAMPTZ)
    -   `updated_at` (TIMESTAMPTZ)

6.  **`payments`** - платежи
    -   `id` (BIGSERIAL, PRIMARY KEY) - уникальный идентификатор платежа
    -   `order_id` (BIGINT, FOREIGN KEY to `orders.id`) - идентификатор бронирования
    -   `amount` (DECIMAL) - сумма платежа
    -   `status` (VARCHAR) - статус платежа (например, "pending", "completed", "failed")
    -   `created_at` (TIMESTAMPTZ)
    -   `updated_at` (TIMESTAMPTZ)

### Масштабирование

-   **Индексы:** Необходимо создать индексы для всех внешних ключей и для полей, которые часто используются 
        в `WHERE` clauses (например, `orders.from_date`, `orders.to_date`, `users.email`).
-   **Партиционирование:** Таблицу `orders` можно партиционировать по дате (`from_date` или `created_at`). 
        Это позволит ускорить запросы, которые фильтруют данные по диапазону дат.
-   **Репликация:** Использовать репликацию для распределения нагрузки между несколькими серверами. 
        Один мастер-сервер для записи и несколько реплик для чтения.
-   **Кэширование:** Кэшировать часто запрашиваемые данные (например, информацию об отелях и типах номеров) 
        в Redis или Memcached.
-   **Шардирование:** В случае экстремально высокой нагрузки можно применить шардирование, разделив данные 
        по какому-либо ключу (например, по `hotel_id` или `user_id`).
